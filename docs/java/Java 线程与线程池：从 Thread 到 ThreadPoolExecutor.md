# Java 线程与线程池：从 Thread 到 ThreadPoolExecutor

## 一、为什么需要线程？

在 Java 中，线程（Thread）是程序执行任务的基本单位之一。一个 Java 程序启动后，通常会有主线程执行入口代码。如果我们希望多个任务能够交替或并发执行，就可以使用多线程。

例如，在一个优惠券系统中，商户上传 Excel 文件后，系统需要统计文件中的用户数量。如果在创建任务的请求中直接读取整个 Excel 文件，那么统计过程就会占用请求处理的时间，用户可能需要等待较长时间才能收到响应。

一种思路是将统计工作交给另一个线程执行，让当前请求线程继续处理后续逻辑。这就是多线程在业务开发中的一个典型应用场景。

需要注意的是，多线程不意味着任务一定会更快。**线程的创建、调度和切换都存在开销；多个线程同时访问共享数据时，还可能产生线程安全问题。**

## 二、使用 Thread 创建线程

Java 可以通过 `Thread` 类创建并启动一个线程。

```
public class ThreadDemo {

    public static void main(String[] args) {
        Thread thread = new Thread(() -> {
            System.out.println("执行异步任务");
        });

        thread.start();

        System.out.println("主线程继续执行");
    }
}
```

这里使用 Lambda 表达式提供任务逻辑。`Thread` 接收一个 `Runnable` 任务，并通过 `start()` 启动新线程。

需要区分 `start()` 和 `run()`：

- `start()`：启动一个新线程，由 JVM 调度该线程执行任务。
- `run()`：普通的方法调用。如果直接调用 `run()`，任务就在当前调用线程中执行，**不会因此启动新线程。**

例如：

```
thread.start(); // 启动新线程
thread.run();   // 普通方法调用
```

在实际开发中，如果只是偶尔执行一个简单的异步任务，直接创建线程可以理解其基本原理。但如果系统需要频繁执行大量任务，每次都创建新线程，就会产生较大的管理和资源开销。

因此，通常需要进一步使用线程池。

## 三、为什么需要线程池？

线程池（Thread Pool）是一种管理和复用工作线程的机制。它接收业务代码提交的任务，并根据自身配置安排线程执行任务。

线程池的主要价值包括：

1. **复用线程。** 任务执行完成后，工作线程通常可以继续执行其他任务，减少频繁创建和销毁线程的开销。
2. **控制并发规模。** 可以限制同时执行任务的线程数量，降低线程过多对 CPU、内存和下游服务造成的压力。
3. **统一管理任务。** 可以通过任务队列、拒绝策略、运行状态和监控机制管理任务的执行过程。

例如，优惠券系统需要统计 Excel 行数时，可以把统计任务提交给线程池。请求线程负责创建任务，线程池中的工作线程负责读取文件和更新统计结果。

从这个角度看，线程池并不是另一种业务任务，而是负责管理任务执行的基础设施。

## 四、ExecutorService 与 ThreadPoolExecutor

Java 提供了 `java.util.concurrent` 包，用于支持并发编程。

其中，`ExecutorService` 是一个接口，提供任务提交、线程池关闭以及通过 `Future` 跟踪异步任务等能力；`ThreadPoolExecutor` 是该接口的一种常见实现，允许开发者显式配置线程池参数。

```
ExecutorService executorService =
        new ThreadPoolExecutor(
                4,
                8,
                60,
                TimeUnit.SECONDS,
                new LinkedBlockingQueue<>(100),
                new ThreadPoolExecutor.AbortPolicy()
        );
```

这段代码创建了一个线程池。这里使用的参数是演示配置，并不意味着所有项目都应该使用这组数值。

`ThreadPoolExecutor` 的主要参数如下：

| 参数                       | 含义                                                         |
| -------------------------- | ------------------------------------------------------------ |
| `corePoolSize`             | 核心线程数，线程池会根据任务提交情况逐步创建核心线程         |
| `maximumPoolSize`          | 允许创建的最大工作线程数                                     |
| `keepAliveTime`            | 非核心线程空闲后等待新任务的时间；默认情况下主要作用于超出核心线程数的线程 |
| `unit`                     | 空闲时间的单位                                               |
| `workQueue`                | 用于暂存等待执行的任务                                       |
| `RejectedExecutionHandler` | 线程池无法接收任务时采用的拒绝策略                           |

以 `corePoolSize = 4`、`maximumPoolSize = 8` 为例**，当任务不断提交时，线程池通常会先创建核心线程；核心线程繁忙后，会尝试将任务放入工作队列。如果队列无法接收任务，线程池才会尝试继续创建线程，直到达到最大线程数。此后仍无法接收的任务将进入拒绝处理流程。**

需要注意，线程池的实际行为与工作队列的类型、容量和拒绝策略密切相关。

## 五、execute() 与 submit()：如何向线程池提交任务？

创建线程池之后，业务代码通常不需要直接操作工作线程，而是提交任务。

### 1. execute()：提交不需要返回结果的任务

```
executorService.execute(() -> {
    System.out.println("开始统计 Excel 行数");
    // 执行统计逻辑
});
```

`execute()` 接收一个 `Runnable` 任务，不返回任务结果，也不提供用于追踪本次任务的 `Future`。

调用 `execute()` 后，调用方通常可以继续执行后续代码，不必等待任务完成。但任务是否能被接收、何时开始执行，取决于线程池的状态、配置和拒绝策略。

### 2. submit()：提交任务并获取 Future

```
Future<Integer> future = executorService.submit(() -> {
    // 模拟统计结果
    return 1000;
});
```

这里的任务返回一个整数，因此可以通过 `submit()` 获取 `Future`。

`Future` 表示一个尚待完成或已经完成的异步计算，可以用于检查任务是否完成、尝试取消任务，以及获取任务结果。

```
Integer result = future.get();
```

调用 `get()` 时，如果任务尚未完成，当前线程会等待结果。如果任务执行失败，获取结果时会抛出 `ExecutionException`；如果等待被中断，则可能抛出 `InterruptedException`。

因此，虽然 `submit()` 不会自动等待任务完成，但如果紧接着调用 `future.get()`，当前线程仍然可能阻塞。

### 3. execute() 与 submit() 的区别

| 对比维度     | execute()                            | submit()                                                     |
| ------------ | ------------------------------------ | ------------------------------------------------------------ |
| 参数         | 通常为 `Runnable`                    | `Runnable` 或 `Callable`                                     |
| 返回值       | `void`                               | `Future`                                                     |
| 获取任务结果 | 不提供直接方式                       | 可以通过 `Future` 获取                                       |
| 任务异常     | 未捕获异常可能交给线程的异常处理机制 | 异常通常由任务执行框架记录在 `Future` 中，并在 `get()` 时体现 |
| 常见场景     | 不需要返回结果的后台任务             | 需要结果、状态查询或取消操作的异步任务                       |

需要特别注意：`submit()` 返回了 `Future`，不代表任务一定执行成功。如果任务被拒绝，仍可能抛出 `RejectedExecutionException`；如果使用静默丢弃等拒绝策略，调用方甚至可能无法仅通过提交方法判断任务是否真正执行。

## 六、工作队列与拒绝策略

线程池不仅需要管理线程，还需要决定线程繁忙时如何处理新任务。

### 1. 常见工作队列

- `LinkedBlockingQueue`：链表实现的阻塞队列，可以配置容量；如果使用无界队列，任务可能不断积压。
- `ArrayBlockingQueue`：基于数组的有界阻塞队列，容量固定。
- `SynchronousQueue`：不存储任务的队列，任务提交需要直接交给一个接收者。

不同队列会影响线程池扩容、任务等待时间和资源占用。

### 2. 常见拒绝策略

`ThreadPoolExecutor` 提供了几种常见拒绝策略：

- `AbortPolicy`：抛出 `RejectedExecutionException`。
- `CallerRunsPolicy`：在满足策略条件时，由提交任务的调用线程执行任务。
- `DiscardPolicy`：直接丢弃被拒绝的任务，不抛出异常。
- `DiscardOldestPolicy`：尝试丢弃队列中最旧的等待任务，再重新提交当前任务。

拒绝策略不是简单的配置选项，而是业务可靠性设计的一部分。

例如，如果线程池负责发送重要订单通知，静默丢弃任务可能造成通知遗漏；如果任务可以被持久化并通过其他机制恢复，则可以结合具体业务设计相应的降级策略。

## 七、结合优惠券项目理解线程池

在优惠券项目中，创建发放任务的方法会执行类似的代码：

```
executorService.execute(
    () -> refreshCouponTaskSendNum(delayJsonObject)
);
```

这里可以拆分为三个部分：

1. `executorService`：线程池对象，负责管理工作线程。
2. `execute()`：向线程池提交任务。
3. `refreshCouponTaskSendNum(...)`：真正执行的业务逻辑，例如读取 Excel 文件并更新数据库中的统计数量。

调用 `execute()` 后，主流程可以继续安排 Redis 延迟任务，并根据发送类型触发后续的优惠券发放流程。

但线程池只负责执行任务，并不提供任务持久化保障。应用重启、任务执行异常、线程池拒绝任务等情况，都可能导致业务工作未能按预期完成。因此，项目才会进一步使用 Redis 延迟队列检查统计结果，并尝试补救。

这里需要区分两种能力：

- **线程池：** 管理线程并执行异步任务。
- **Redis 延迟队列：** 延迟投递任务，供消费者在之后检查或处理。

两者解决的问题不同，不能简单地认为使用线程池就能保证任务可靠完成。

## 八、线程池使用中的注意事项

在实际 Java 开发中，理解线程池的基本原理之后，还需要注意以下问题：

1. **线程数量不能随意设置。** 需要结合任务属于 CPU 密集型还是 I/O 密集型、服务器资源和下游服务容量进行评估。
2. **合理设置队列容量。** 无界队列可能造成任务积压和内存压力；过小的队列则可能导致任务频繁被拒绝。
3. **关注异常处理。** 异步任务中的异常不一定会直接反馈给发起请求的线程，需要设计合适的日志、监控和失败处理机制。
4. **避免共享数据的并发问题。** 多个工作线程同时访问可变对象时，需要评估线程安全性。
5. **正确关闭线程池。** 通常应在应用关闭时停止接收新任务，并根据需要等待已提交任务完成。
6. **不要把异步执行等同于可靠执行。** 如果业务任务不能丢失，就需要结合持久化任务、消息队列、重试、幂等和补偿等机制进行设计。

## 九、总结

线程是程序执行任务的基本单位之一，`Thread` 可以用于创建并启动线程；线程池则进一步提供线程复用、并发控制和任务管理能力。

在 Java 项目中，`ExecutorService` 是常用的任务执行接口，`ThreadPoolExecutor` 是灵活的线程池实现。业务代码通过 `execute()` 或 `submit()` 提交任务，其中 `submit()` 还可以返回 `Future`，用于跟踪任务状态和获取结果。

学习线程池时，不应只记忆构造方法中的参数，还应该理解任务提交后，线程池如何选择创建线程、使用队列，以及在无法接收任务时执行拒绝策略。

最后，线程池解决的是任务如何执行的问题，而不是任务如何可靠地保存、恢复和完成的问题。理解这一区别，是从掌握 Java 并发 API 迈向实际工程开发的重要一步。
